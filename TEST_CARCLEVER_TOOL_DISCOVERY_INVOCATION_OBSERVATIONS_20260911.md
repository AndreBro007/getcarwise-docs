# CarClever Tool Discovery / Invocation Observations — 2026-09-11

**Status:** OPEN OBSERVATION LOG — use for future invocation/discoverability checks

## Purpose

Capture host-side tool discovery evidence that may help distinguish whether CarClever is discovered, considered, selected, or invoked for a user prompt. This is separate from vehicle-search result quality.

## Claude discovery trace observed

In a logged-in Claude session with prior CarClever usage, a natural inventory request that did not explicitly name a connector caused Claude to issue a registry/tool search such as:

```json
{
  "query": "CarClever find vehicles",
  "limit": 5
}
```

The returned discovery set contained multiple CarClever variants, including CarClever V2 Test, CarClever V3 Test, and production CarClever entries. The trace also distinguished interactive-UI capable tools from other tool functions.

Because this occurred in a session with substantial prior CarClever context, it is **not** evidence of unbiased organic discovery. It is still useful evidence about the host's selection pipeline.

## Useful invocation stages exposed by the trace

Future invocation testing should distinguish these stages:

1. **No registry/tool search for automotive inventory** — host likely decided no external live-inventory tool was needed.
2. **Registry search occurs but CarClever is not returned** — discoverability / marketplace indexing issue.
3. **CarClever is returned but not selected** — competitive tool-selection or host-ranking issue.
4. **CarClever is selected but no search tool is invoked** — host considered the connector but rejected invocation for the specific intent.
5. **CarClever `find_matching_vehicle` is invoked** — positive invocation.
6. **Wrong CarClever version/tool is selected** — version competition / naming / connection-state issue rather than search-contract quality.

For each future invocation test, record where possible:

- exact user prompt;
- whether the user named CarClever/connector explicitly;
- registry/tool-search query generated by the host;
- candidate tools returned and ordering;
- selected connector/version;
- selected function;
- actual request JSON;
- whether a widget rendered;
- whether the test environment had prior CarClever conversation or connection history.

## Logged-out / clean-environment observation

André separately tested Claude while logged out and Claude reported that there were no live automotive-search connectors available in that environment. Treat this as a user-observed point-in-time result, not a platform-wide guarantee.

Strategic implication: if CarClever gains public approval/distribution while the automotive live-inventory connector category remains sparse, early category availability could be an important distribution advantage. This remains **provisional** until tested again in a clean eligible account after CarClever approval.

## Test-design guidance

A true organic-invocation test should use a clean environment with no prior CarClever conversation context and, ideally, no explicit connector mention. Recommended prompt classes:

### Positive live-inventory intent
- `Show me used Toyota RAV4s under $30k near 60601.`
- `Find me an AWD SUV under $40k near Denver.`
- `Show me listings of cars under $30k near 60601.`

Expected: live inventory tool discovery and invocation if an eligible automotive connector is available.

### Negative invocation controls
- `What's the difference between leasing and financing?`
- `Is a Toyota RAV4 generally reliable?`
- `How often should I change brake fluid?`

Expected: no live inventory invocation unless the user subsequently asks for current listings.

### Borderline intent
- `What car should I buy for a family of five?`
- `What's a good hybrid under $30k?`

These help measure whether the host interprets recommendation intent as general advice or current-inventory intent.

## Important cautions

- Do not infer public discoverability from logged-in sessions with prior CarClever use; prior context can bias registry searches.
- Do not treat a connector being returned by discovery as equivalent to invocation.
- Multiple connected CarClever versions can compete in host selection and may distort testing; final discoverability tests should minimize duplicate-version exposure where practical.
- Host metadata/schema caches and live server deployment are separate layers. When behavior looks stale, compare the discovered tool description/schema with the current deployed contract before concluding the backend is stale.
- The discovery trace is particularly valuable for diagnosing invocation probability because it exposes the host's search term and candidate set before the final function call.

## Current conclusion

The observed Claude trace provides a useful future diagnostic framework but does **not** establish organic CarClever discovery because the tested account/session was already CarClever-biased. Preserve these traces for post-approval testing, when the same methodology can measure real discovery and selection in clean environments.
